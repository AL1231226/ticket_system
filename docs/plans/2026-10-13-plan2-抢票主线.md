# 演出票务平台 Plan 2：抢票主线（Lua 原子扣减 + Stream 异步下单 + 订单状态机）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 `ticket_back` 从「能浏览演出」推进到「能完整走完一次抢票」——用户选定票档 → Lua 脚本原子扣减库存与限购校验 → Redis Stream 异步落库 → 前端轮询拿到订单 → 模拟支付 → 票夹里出现一张带二维码的票。

**Architecture:** 开票瞬间的写入压力全部落在 Redis 上：库存扣减、限购校验、下单消息投递三步写进同一个 `seckill.lua`，脚本执行期间 Redis 单线程不插入其他命令，**天然原子**。MySQL 退到异步侧——独立的消费者线程读 `stream.orders`，在事务里扣 DB 库存 + 累加限购兜底表 + 落订单，把几十万 QPS 削到自己扛得住的节奏。读路径（余量查询、订单轮询、票夹）走普通同步查询，不参与并发。

**Tech Stack:** Spring Boot 3.5.16 · Java 17 · MyBatis-Plus 3.5.17 · Redis (Lettuce + Lua + Stream) · Redisson 3.52.0 · MySQL 8.4 · JUnit 5 · AssertJ

### 实测 A：所有公开读接口都返回 401 ★硬阻塞★

```bash
curl -w " [%{http_code}]" http://localhost:8081/api/show/1                       # 401
curl -w " [%{http_code}]" "http://localhost:8081/api/show/list/byCategory?categoryId=1"  # 401
curl -w " [%{http_code}]" http://localhost:8081/api/show/category/list           # 401
```

带上有效 token 后三个都正常（`/api/show/1` 返回演出 + 3 个场次 + 每个场次 3 个票档，`minPrice=480`）。

**原因**：`config/mvcConfig.java` 里 `LoginInterceptor` 用的是 hmdp 遗留的排除清单——`/shop/**`、`/shop-type/**`、`/voucher/**`、`/blog/hot`。本项目根本没有这些路径，而 `/show/**`、`/venue/**` 一个都没被放行，于是「除了这几个路径，全都要登录」。

**为什么阻塞 Plan 2**：抢票页要展示票档、要轮询余量、详情页要对未登录用户可见。这条不修，后面的验收命令全部跑不通。→ **Task 1**

### 实测 B：任意一次带 token 的请求都会把 token 寿命从 25 天砍到 10 小时

```bash
# 登录后立刻查 TTL
docker exec ticket_redis redis-cli -a 123456 --no-auth-warning TTL "login:token:<token>"
# → 2159999   （≈25 天 = LOGIN_USER_TTL 36000 分钟）

# 用这个 token 发任意一个请求（/user/me 或 /user/sign）
# 再查 TTL
# → 36000     （10 小时）
```

**原因**：`utils/flashInterceptor.java` 第 43 行续期写的是 `TimeUnit.SECONDS`，而 `UserServiceImpl.login` 用的是 `TimeUnit.MINUTES`。同一个常量 `LOGIN_USER_TTL = 36000`，一处当分钟一处当秒。→ **Task 1**

### 实测 C：假 token **不会**绕过鉴权（与之前的判断相反）

```bash
curl -w " [%{http_code}]" -X POST -H "authorization: fake-token-xyz" http://localhost:8081/api/user/sign
# → 401
```

`flashInterceptor` 在 token 无效时写了 `response.setStatus(401); return true;`，随后 `LoginInterceptor` 因为 `UserHolder` 里没人，也会 `setStatus(401); return false` 把请求拦下。所以**当前的鉴权没有被绕过**。

> 之前记录里"伪造 token 能通过鉴权"的说法，证据是 Redis 里那条残留的 `sign:null2026-10` 键——那是更早版本的代码留下的，当时的拦截器配置和现在不一样。**别按"要把 `return true` 改成 `return false`"的思路去修**，那样改会把公开接口也拦死。正确的修法见 Task 1 Step 2。

```java
@Configuration

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
```

- [ ] **Step 2: 修 `flashInterceptor` 的两个缺陷**

`src/main/java/com/liule/ticket/utils/flashInterceptor.java` 的 `preHandle` 方法替换为：

```java
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        // 获取token
        String token = request.getHeader("authorization");
        if (token == null) {
            // 没带 token 也放行 —— 公开接口不需要登录，到底要不要拦由 LoginInterceptor 决定
            return true;
        }
        // 查询redis,取用戶
        Map<Object, Object> usermap = stringRedisTemplate.opsForHash().entries(LOGIN_USER_KEY + token);

        // token 无效或已过期：不加载用户，直接放行。
        //
        // 这里不能写 response.setStatus(401)。本拦截器挂在 /** 上，公开接口（演出列表、详情）
        // 也要过它；一旦设了状态码，带过期 token 的用户访问详情页就会拿到
        // 「HTTP 401 + 正常的 JSON body」，前端 axios 会误判成掉线并跳登录页。
        // 该不该 401，是 LoginInterceptor 的职责。
        if (usermap.isEmpty()) {
            return true;
        }
        // 保存用户
        UserDTO user = BeanUtil.fillBeanWithMap(usermap, new UserDTO(), false);

        UserHolder.saveUser(user);
        // 刷新有效期
        //
        // 单位必须是 MINUTES：UserServiceImpl.login 里用的是 TimeUnit.MINUTES，
        // 同一个常量 LOGIN_USER_TTL 两处单位不一致的话，第一次带 token 的请求
        // 就会把 25 天的 token 砍成 10 小时（36000 秒）。实测过。
        stringRedisTemplate.expire(LOGIN_USER_KEY + token, LOGIN_USER_TTL, TimeUnit.MINUTES);
        // 放行
        return true;
    }
```

> 其余部分（`afterCompletion`、构造函数、import）保持不动。`usermap` 的声明类型沿用原来的 `Map<Object, Object>`。

```java
package com.liule.ticket.mapper;

import com.baomidou.mybatisplus.core.mapper.BaseMapper;
import com.liule.ticket.entity.UserPurchase;
import org.apache.ibatis.annotations.Insert;
import org.apache.ibatis.annotations.Param;
import org.apache.ibatis.annotations.Select;
import org.apache.ibatis.annotations.Update;

public interface UserPurchaseMapper extends BaseMapper<UserPurchase> {

    /**
     * 累加某用户在某场次的已购数量。
     * <p>
     * 唯一索引 uk_user_session 是这里的并发安全基础：同一用户并发下单时，
     * 只有一个事务能 INSERT 成功，其余的都被唯一索引挡下来走 UPDATE 分支，
     * 所以 quantity 不会因为并发而少算。
     * <p>
     * 用 {@code AS new} 别名而不是 {@code VALUES(quantity)} —— 后者从 MySQL 8.0.20 起废弃。
     * 右边的列名必须带表名限定写成 {@code tb_user_purchase.quantity}，
     * 只写 {@code quantity} 会和 {@code new.quantity} 撞成歧义列，报 ERROR 1052。
     */
    @Insert("INSERT INTO tb_user_purchase (user_id, session_id, quantity) " +
            "VALUES (#{userId}, #{sessionId}, #{quantity}) AS new " +
            "ON DUPLICATE KEY UPDATE quantity = tb_user_purchase.quantity + new.quantity")
    int increase(@Param("userId") Long userId,
                 @Param("sessionId") Long sessionId,
                 @Param("quantity") Integer quantity);

    /**
     * 查已购数量，没有记录时返回 null
     */
    @Select("SELECT quantity FROM tb_user_purchase WHERE user_id = #{userId} AND session_id = #{sessionId}")
    Integer getQuantity(@Param("userId") Long userId, @Param("sessionId") Long sessionId);

    /**
     * 取消/退票时把已购数减回去 —— 不减的话，用户取消后想重买会被自己之前那次计数挡住。
     * <p>
     * WHERE 里的 {@code quantity >= #{quantity}} 不能省：quantity 是 UNSIGNED 列，
     * 减到负数是 MySQL 报错（BIGINT UNSIGNED value is out of range），不是截断成 0。
     * 加上这个条件，不够减时直接 0 行受影响，静静地什么都不做。
     */
    @Update("UPDATE tb_user_purchase SET quantity = quantity - #{quantity} " +
            "WHERE user_id = #{userId} AND session_id = #{sessionId} AND quantity >= #{quantity}")
    int decrease(@Param("userId") Long userId,
                 @Param("sessionId") Long sessionId,
                 @Param("quantity") Integer quantity);

}
```

```java
    @Override
    public Long queryStock(Long tierId) {
        String key = SECKILL_STOCK_KEY + tierId;
        String cached = stringRedisTemplate.opsForValue().get(key);
        if (cached != null) {
            return Long.valueOf(cached);
        }
        TicketTier tier = getById(tierId);
        if (tier == null) {
            return null;
        }
        // 无 TTL（见 RedisConstants 上的说明）。Redis 重启丢了这个 key 也不会不一致：
        // 未落库的下单消息跟它一起丢了，DB 里的 stock 也没扣，两边仍然对得上。
        stringRedisTemplate.opsForValue()
                .setIfAbsent(key, String.valueOf(tier.getStock()));
        return tier.getStock().longValue();
    }

    @Override
    public int preloadStock() {
        List<TicketTier> tiers = list(new LambdaQueryWrapper<TicketTier>()
                .eq(TicketTier::getStatus, 1));

        int loaded = 0;
        for (TicketTier tier : tiers) {
            Boolean created = stringRedisTemplate.opsForValue()
                    .setIfAbsent(SECKILL_STOCK_KEY + tier.getId(), String.valueOf(tier.getStock()));
            if (Boolean.TRUE.equals(created)) {
                loaded++;
            }
        }
        return loaded;
    }
```

```java
     * 例：/ticket-tier/1
     */
    @GetMapping("/{tierId}")
    public Result stock(@PathVariable("tierId") Long tierId) {
        Long stock = ticketTierService.queryStock(tierId);
        if (stock == null) {
            return Result.fail("票档不存在");
        }
        return Result.ok(stock);
    }

    /**
     * 把所有上架票档的余量预热进 Redis。开票前手工调一次。
     * 幂等，重复调不会覆盖已经扣减的库存。
     */
    @PostMapping("/preload")
    public Result preload() {
        return Result.ok(ticketTierService.preloadStock());
    }

}
```

`src/main/resources/lua/seckill.lua`：

```lua
-- 抢票原子脚本
-- Redis 执行 Lua 期间是单线程的，脚本里不会插进别的命令，
-- 所以「查库存 → 查限购 → 扣库存 → 加计数 → 发消息」对外是一个原子操作。
--
-- KEYS[1] = seckill:stock:{tierId}        剩余库存
-- KEYS[2] = seckill:ordered:{sessionId}   限购计数 Hash，field = userId
-- KEYS[3] = stream.orders                 下单消息流
-- ARGV[1] = userId
-- ARGV[2] = orderId
-- ARGV[3] = quantity       购买数量
-- ARGV[4] = purchaseLimit  限购上限
-- ARGV[5] = tierId
-- ARGV[6] = sessionId
--
-- 返回：0 成功 / 1 售罄 / 2 超出限购

local stock = redis.call('GET', KEYS[1])
if (not stock) or (tonumber(stock) < tonumber(ARGV[3])) then
    return 1
end

local bought = tonumber(redis.call('HGET', KEYS[2], ARGV[1]) or '0')
if bought + tonumber(ARGV[3]) > tonumber(ARGV[4]) then
    return 2
end

redis.call('DECRBY', KEYS[1], ARGV[3])
redis.call('HINCRBY', KEYS[2], ARGV[1], ARGV[3])
redis.call('XADD', KEYS[3], '*',
    'orderId',   ARGV[2],
    'userId',    ARGV[1],
    'tierId',    ARGV[5],
    'sessionId', ARGV[6],
    'quantity',  ARGV[3])

return 0
```

三点说明：

1. **`stream.orders` 挪进 `KEYS` 而不是照设计文档写死在脚本里**。Redis 官方要求「脚本访问的所有 key 都从 KEYS 传」，这样在 Redis Cluster 下才能正确算出 key 的 slot；写死的话脚本跨 slot 会直接报错。顺带一个好处：测试可以传 `seckill:test:stream` 进来，不污染真实消息流。
2. **先校验再扣减**，不是原版那种「先 DECR 再看是否 < 0、是就 INCR 回补」。除了少一次无效写，更重要的是这样能支持 `quantity > 1` 的批量扣减。
3. **`not stock`（key 不存在）归到"售罄"**。所以 Java 侧必须保证调用前库存 key 一定存在，否则用户会看到假售罄——见 Step 3。

```java
package com.liule.ticket.service;

import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.core.io.ClassPathResource;
import org.springframework.data.redis.core.StringRedisTemplate;

import java.util.Collections;
import java.util.List;
import java.util.Set;

import java.util.concurrent.Executors;

import static org.assertj.core.api.Assertions.assertThat;

/**
 * seckill.lua 的行为验证：三种返回码、不超卖、限购在并发下也准。
 * 全部用 seckill:test:* 前缀的 key，结束后清干净，不碰真实的 seckill:stock:*。
 */
@SpringBootTest
class SeckillScriptTest {

    private static final String STOCK_KEY = "seckill:test:stock:1";
    private static final String ORDERED_KEY = "seckill:test:ordered:1";
    private static final String STREAM_KEY = "seckill:test:stream";

    private static final DefaultRedisScript<Long> SECKILL_SCRIPT;

    static {
        SECKILL_SCRIPT = new DefaultRedisScript<>();
        SECKILL_SCRIPT.setLocation(new ClassPathResource("lua/seckill.lua"));
        SECKILL_SCRIPT.setResultType(Long.class);
    }

    @Autowired
    private StringRedisTemplate stringRedisTemplate;

    @AfterEach
    void cleanUp() {
        stringRedisTemplate.delete(Arrays.asList(STOCK_KEY, ORDERED_KEY, STREAM_KEY));
    }

    /** 执行脚本，返回码 0 成功 / 1 售罄 / 2 超限购 */
    private long run(Long userId, Long orderId, int quantity, int limit) {
        Long r = stringRedisTemplate.execute(
                SECKILL_SCRIPT,
                Arrays.asList(STOCK_KEY, ORDERED_KEY, STREAM_KEY),
                userId.toString(), orderId.toString(), String.valueOf(quantity),
                String.valueOf(limit), "1", "1");
        return r == null ? -1 : r;
    }

    @Test
    void successDeductsStockAndPublishesMessage() {
        stringRedisTemplate.opsForValue().set(STOCK_KEY, "10");

        assertThat(run(1001L, 90001L, 2, 4)).isZero();

        assertThat(stringRedisTemplate.opsForValue().get(STOCK_KEY)).isEqualTo("8");
        assertThat(stringRedisTemplate.opsForHash().get(ORDERED_KEY, "1001")).isEqualTo("2");

        // 消息真的进了 stream，且带全了消费者需要的六个字段
        Set<String> keys = stringRedisTemplate.keys(STREAM_KEY);
        assertThat(keys).isNotEmpty();
        assertThat(stringRedisTemplate.opsForStream().size(STREAM_KEY)).isEqualTo(1L);
    }

    @Test
    void soldOutReturns1AndTouchesNothing() {
        stringRedisTemplate.opsForValue().set(STOCK_KEY, "1");

        assertThat(run(1001L, 90001L, 2, 4)).isEqualTo(1);

        // 失败时库存和限购计数都不该被改动
        assertThat(stringRedisTemplate.opsForValue().get(STOCK_KEY)).isEqualTo("1");
        assertThat(stringRedisTemplate.opsForHash().hasKey(ORDERED_KEY, "1001")).isFalse();
        assertThat(stringRedisTemplate.opsForStream().size(STREAM_KEY)).isZero();
    }

    @Test
    void missingStockKeyIsTreatedAsSoldOut() {
        // key 不存在 → 返回 1。
        // 这条测试是在钉住一个"必须由调用方负责"的前提：抢票前一定要先把库存预热进 Redis，
        // 否则用户看到的是"售罄"而不是"系统没准备好"。
        assertThat(run(1001L, 90001L, 1, 4)).isEqualTo(1);
    }

    @Test
    void overPurchaseLimitReturns2() {
        stringRedisTemplate.opsForValue().set(STOCK_KEY, "100");

        assertThat(run(1001L, 90001L, 2, 2)).isZero();     // 已买 2
        assertThat(run(1001L, 90002L, 1, 2)).isEqualTo(2); // 再买 1 就超了

        assertThat(stringRedisTemplate.opsForValue().get(STOCK_KEY)).isEqualTo("98");
    }

    @Test
    void stockNeverGoesNegativeUnderConcurrency() throws InterruptedException {
        int stock = 20;
        int threads = 100;
        stringRedisTemplate.opsForValue().set(STOCK_KEY, String.valueOf(stock));

        AtomicInteger success = new AtomicInteger();
        CountDownLatch ready = new CountDownLatch(threads);
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(threads);

        ExecutorService pool = Executors.newFixedThreadPool(threads);
        try {
            for (int i = 0; i < threads; i++) {
                final long userId = 2000 + i;
                pool.submit(() -> {
                    ready.countDown();
                    try {
                        start.await(); // 100 个线程一起发车，制造真实竞争
                        if (run(userId, userId, 1, 4) == 0) {
                            success.incrementAndGet();
                        }
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    } finally {
                        done.countDown();
                    }
                });
            }
            assertThat(ready.await(10, TimeUnit.SECONDS)).isTrue();
            start.countDown();
            assertThat(done.await(30, TimeUnit.SECONDS)).isTrue();
        } finally {
            pool.shutdownNow();
        }

        // 20 个库存、100 个人抢、每人限购 4 → 成功数必须正好等于库存数
        assertThat(success.get()).isEqualTo(stock);
        assertThat(stringRedisTemplate.opsForValue().get(STOCK_KEY)).isEqualTo("0");
        // 消息条数 = 成功数，一条不多一条不少
        assertThat(stringRedisTemplate.opsForStream().size(STREAM_KEY)).isEqualTo((long) stock);
    }

}
```

```java
package com.liule.ticket.service.impl;

import com.baomidou.mybatisplus.spring.service.impl.ServiceImpl;
import com.liule.ticket.dto.Result;
import com.liule.ticket.dto.SeckillFormDTO;
import com.liule.ticket.entity.ShowSession;
import com.liule.ticket.entity.TicketOrder;
import com.liule.ticket.entity.TicketTier;
import com.liule.ticket.mapper.TicketOrderMapper;
import com.liule.ticket.service.IOrderService;
import com.liule.ticket.service.IShowSessionService;
import com.liule.ticket.service.ITicketTierService;
import com.liule.ticket.utils.RedisConstants;
import com.liule.ticket.utils.RedisIdWorker;
import com.liule.ticket.utils.UserHolder;
import jakarta.annotation.Resource;
import lombok.extern.slf4j.Slf4j;
import org.springframework.core.io.ClassPathResource;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.stereotype.Service;

import java.time.LocalDateTime;
import java.util.Arrays;

@Slf4j
@Service
public class OrderServiceImpl extends ServiceImpl<TicketOrderMapper, TicketOrder>
        implements IOrderService {

    private static final DefaultRedisScript<Long> SECKILL_SCRIPT;

    static {
        SECKILL_SCRIPT = new DefaultRedisScript<>();
        SECKILL_SCRIPT.setLocation(new ClassPathResource("lua/seckill.lua"));
        SECKILL_SCRIPT.setResultType(Long.class);
    }

    @Resource
    private ITicketTierService ticketTierService;

    @Resource
    private IShowSessionService showSessionService;

    @Resource
    private StringRedisTemplate stringRedisTemplate;

    @Resource
    private RedisIdWorker redisIdWorker;

    @Override
    public Result seckill(SeckillFormDTO form) {
        Long userId = UserHolder.getUser().getId();
        Long tierId = form.getTierId();
        Integer quantity = form.getQuantity();

        if (tierId == null) {
            return Result.fail("票档不能为空");
        }
        if (quantity == null || quantity < 1) {
            return Result.fail("购买数量不合法");
        }

        // ---- 下面几步是"前置校验"，用一次主键查询换掉 Lua 里的分支 ----
        // 放在 Redis 之外是有意的：票档上架状态、场次开票时间这些是低频变更的配置数据，
        // 没必要为了省这一次单行查询把它们也塞进 Redis。

        TicketTier tier = ticketTierService.getById(tierId);
        if (tier == null || !Integer.valueOf(1).equals(tier.getStatus())) {
            return Result.fail("票档不存在或已下架");
        }
        if (quantity > tier.getPurchaseLimit()) {
            return Result.fail("本票档每账号限购 " + tier.getPurchaseLimit() + " 张");
        }

        ShowSession session = showSessionService.getById(tier.getSessionId());
        if (session == null) {
            return Result.fail("场次不存在");
        }
        // 0未开票 1预售中 2已开票 3已售罄 4已结束 5已取消 —— 只有 1、2 能抢
        if (!Integer.valueOf(1).equals(session.getStatus())
                && !Integer.valueOf(2).equals(session.getStatus())) {
            return Result.fail("本场次当前不可抢票");
        }
        if (session.getOnSaleTime().isAfter(LocalDateTime.now())) {
            return Result.fail("还未到开票时间");
        }

        // 确保 Redis 里有这个票档的库存 key。
        // 少了这一步，没预热过的票档在 Lua 里 GET 到 nil，会被当成"售罄"返回给用户 —— 假售罄。
        ticketTierService.queryStock(tierId);

        // 订单号先在外面生成好再传给脚本：Lua 里没法方便地生成全局唯一ID，
        // 而且订单号提前生成好，消息里带的 id 和接口返回给前端的 id 是同一个。
        //
        // 风控限流的滑动窗口校验将来插在这一行之前（Plan 3）—— 放在这里是因为
        // 它要在"已经通过票档校验、还没生成订单号"的位置上，被拦下的请求不该占用订单号。
        Long orderId = redisIdWorker.create_ID("order");

        Long r = stringRedisTemplate.execute(
                SECKILL_SCRIPT,
                Arrays.asList(RedisConstants.SECKILL_STOCK_KEY + tierId,
                        RedisConstants.SECKILL_ORDERED_KEY + tier.getSessionId(),
                        RedisConstants.ORDER_STREAM_KEY),
                userId.toString(),
                orderId.toString(),
                quantity.toString(),
                tier.getPurchaseLimit().toString(),
                tierId.toString(),
                tier.getSessionId().toString());

        int code = r == null ? -1 : r.intValue();
        if (code == 1) {
            return Result.fail("已售罄");
        }
        if (code == 2) {
            return Result.fail("超出限购数量");
        }
        if (code != 0) {
            return Result.fail("系统繁忙，请重试");
        }
        // 此刻只是"抢到了名额"，订单还没落库。前端拿 orderId 去 /order/result/{orderId} 轮询。
        return Result.ok(orderId);
    }

}
```

往 `OrderServiceImpl` 补：`@Resource private UserPurchaseMapper userPurchaseMapper;`

```java
    @Override
    @Transactional(rollbackFor = Exception.class)
    public void createOrder(Long orderId, Long userId, Long tierId, Long sessionId, Integer quantity) {
        TicketTier tier = ticketTierService.getById(tierId);
        if (tier == null) {
            throw new BizException("票档不存在");
        }

        // 1. 扣 DB 库存。
        //    ge("stock", quantity) 让"库存不够"表现为影响 0 行，而不是扣成负数。
        //    这就是原版 Lua 里"先 DECR 再判断 < 0"那条判断在 DB 侧的等价物。
        //    setSql 拼的是 Integer，进这个方法前已经被 seckill 校验过 1..purchaseLimit，不存在注入。
        //    ⚠ stock 和 lock_stock 必须在【同一条 UPDATE】里改。拆成两条的话，
        //    中间那一刻 total_stock ≠ stock + lock_stock，并发校验会误报。
        //    三元组的语义见 tb_ticket_tier 的建表注释。
        boolean ok = ticketTierService.update()
                .setSql("stock = stock - " + quantity
                        + ", lock_stock = lock_stock + " + quantity)
                .eq("id", tierId)
                .ge("stock", quantity)
                .update();
        if (!ok) {
            throw new BizException("库存不足，订单创建失败");
        }

        // 2. 限购兜底。
        //    Redis 是限购的主判据（快、原子），但它可能被清空或重启丢数据，
        //    所以这里在同一事务里再累加一次并校验 —— 唯一索引 + 原子累加，
        //    即使 Redis 全丢了也不会超卖。
        userPurchaseMapper.increase(userId, sessionId, quantity);
        Integer total = userPurchaseMapper.getQuantity(userId, sessionId);
        if (total != null && total > tier.getPurchaseLimit()) {
            throw new BizException("超出限购，事务回滚");
        }

        // 3. 落订单
        TicketOrder order = new TicketOrder()
                .setId(orderId)
                .setUserId(userId)
                .setShowId(tier.getShowId())
                .setSessionId(sessionId)
                .setTierId(tierId)
                .setQuantity(quantity)
                .setAmount(tier.getPrice().multiply(BigDecimal.valueOf(quantity)))
                .setStatus(0)
                .setSource(0)
                .setExpireTime(LocalDateTime.now().plusMinutes(SystemConstants.ORDER_PAY_TIMEOUT_MINUTES));
        save(order);
    }
```

补 import：`com.liule.ticket.exception.BizException`、`com.liule.ticket.mapper.UserPurchaseMapper`、`com.liule.ticket.utils.SystemConstants`、`org.springframework.transaction.annotation.Transactional`、`java.math.BigDecimal`。

`src/main/java/com/liule/ticket/mq/OrderStreamConsumer.java`：

```java
package com.liule.ticket.mq;

import com.liule.ticket.service.IOrderService;
import com.liule.ticket.utils.RedisConstants;
import jakarta.annotation.Resource;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.DisposableBean;
import org.springframework.beans.factory.InitializingBean;
import org.springframework.data.redis.connection.stream.Consumer;
import org.springframework.data.redis.connection.stream.MapRecord;
import org.springframework.data.redis.connection.stream.ReadOffset;
import org.springframework.data.redis.connection.stream.StreamOffset;
import org.springframework.data.redis.connection.stream.StreamReadOptions;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

import java.time.Duration;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

/**
 * 下单消息的消费者。
 * <p>
 * 只做三件事：反序列化消息 → 调 {@code IOrderService.createOrder} → ACK。
 * 全部业务逻辑在 service 里，这里出问题只可能是"消息没读到"或"没 ACK 掉"。
 * <p>
 * 单独起线程而不是用缓存重建那个线程池：两者语义不同，混在一起会让
 * "缓存重建慢"把"订单落库"堵住，反过来也一样。
 */
@Slf4j
@Component
public class OrderStreamConsumer implements InitializingBean, DisposableBean {

    private static final String STREAM = RedisConstants.ORDER_STREAM_KEY;
    private static final String GROUP = RedisConstants.ORDER_STREAM_GROUP;
    private static final String CONSUMER = RedisConstants.ORDER_STREAM_CONSUMER;

    /** 阻塞读的超时。设太长会让线程无法及时退出，太短则空转浪费 CPU */
    private static final Duration BLOCK_TIMEOUT = Duration.ofSeconds(2);

    @Resource
    private StringRedisTemplate stringRedisTemplate;

    @Resource
    private IOrderService orderService;

    private ExecutorService pool;

    @Override
    public void afterPropertiesSet() {
        initGroup();
        pool = Executors.newSingleThreadExecutor(r -> {
            Thread t = new Thread(r, "order-stream-consumer");
            t.setDaemon(true);
            return t;
        });
        pool.submit(this::consume);
        log.info("下单消息消费者已启动：{}/{}/{}", STREAM, GROUP, CONSUMER);
    }

    @Override
    public void destroy() {
        if (pool != null) {
            pool.shutdownNow();
        }
    }

    /** 建消费者组。组已存在时 Redis 返回 BUSYGROUP，属于正常情况，吞掉即可。 */
    private void initGroup() {
        try {
            stringRedisTemplate.opsForStream().createGroup(STREAM, ReadOffset.from("0"), GROUP);
            log.info("已创建消费者组 {}/{}", STREAM, GROUP);
        } catch (Exception e) {
            String msg = e.getCause() == null ? e.getMessage() : e.getCause().getMessage();
            if (msg != null && msg.contains("BUSYGROUP")) {
                log.info("消费者组 {}/{} 已存在，跳过创建", STREAM, GROUP);
            } else {
                throw e;
            }
        }
    }

    private void consume() {
        while (!Thread.currentThread().isInterrupted()) {
            try {
                // 1) 先读新消息（会阻塞最多 2 秒）
                List<MapRecord<String, Object, Object>> records = stringRedisTemplate.opsForStream().read(
                        Consumer.from(GROUP, CONSUMER),
                        StreamReadOptions.empty().count(1).block(BLOCK_TIMEOUT),
                        StreamOffset.create(STREAM, ReadOffset.lastConsumed()));

                if (records != null && !records.isEmpty()) {
                    handle(records);
                    continue;
                }

                // 2) 没有新消息，再去捞本消费者名下的 pending。
                //    pending = 已经投递给 c1、但还没 ACK 的消息，通常是上一次进程崩溃时留下的。
                //    不处理 pending 的话这些订单永远不会落库，而用户那边一直在"排队中"。
                handlePending();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            } catch (Exception e) {
                if (Thread.currentThread().isInterrupted()) {
                    break;
                }
                log.error("消费下单消息失败", e);
            }
        }
        log.info("下单消息消费者已停止");
    }

    private void handlePending() {
        List<MapRecord<String, Object, Object>> pending = stringRedisTemplate.opsForStream().read(
                Consumer.from(GROUP, CONSUMER),
                StreamReadOptions.empty().count(1),
                StreamOffset.create(STREAM, ReadOffset.from("0")));
        if (pending != null && !pending.isEmpty()) {
            log.info("发现 {} 条 pending 消息，重新处理", pending.size());
            handle(pending);
        }
    }

    private void handle(List<MapRecord<String, Object, Object>> records) {
        for (MapRecord<String, Object, Object> record : records) {
            Map<Object, Object> value = record.getValue();
            try {
                Long orderId = Long.valueOf(String.valueOf(value.get("orderId")));

                // 幂等：消息可能因为"落库成功但 ACK 之前进程挂了"而重投。
                // 不做这一步的话，同一张票会被扣两次库存。
                if (orderService.getById(orderId) != null) {
                    log.info("订单 {} 已存在，跳过重复消费", orderId);
                } else {
                    orderService.createOrder(
                            orderId,
                            Long.valueOf(String.valueOf(value.get("userId"))),
                            Long.valueOf(String.valueOf(value.get("tierId"))),
                            Long.valueOf(String.valueOf(value.get("sessionId"))),
                            Integer.valueOf(String.valueOf(value.get("quantity"))));
                    log.info("订单 {} 落库成功", orderId);
                }
            } catch (Exception e) {
                // 这里吞掉异常是有意的：库存不足、超出限购这类失败重试多少次都一样，
                // 一直不 ACK 会把消费者卡在这一条消息上，后面的订单全部积压。
                // 代价是这条消息丢了 —— 日志里有完整记录，且 Redis 侧的库存/限购计数
                // 在这个订单重试时已经被算进去了，本来也不该再重试。
                log.error("下单消息处理失败，已丢弃：{}", record.getId(), e);
            } finally {
                stringRedisTemplate.opsForStream().acknowledge(STREAM, GROUP, record.getId());
            }
        }
    }

}
```

> **为什么异常也要 ACK**：这是 Stream 消费绕不开的取舍。不 ACK 的话消息会一直留在 PEL 里，消费者每轮都先处理它，后面的消息永远轮不到——一条毒消息堵死整条队列。代价是这条订单丢了，用户会一直停在"排队中"，需要人工/巡检兜底。Plan 3 可以加一个"重试 N 次后投到死信 stream"的机制。

```java
package com.liule.ticket.service;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.liule.ticket.entity.TicketOrder;
import com.liule.ticket.entity.TicketTier;
import com.liule.ticket.entity.UserPurchase;
import com.liule.ticket.exception.BizException;
import com.liule.ticket.mapper.UserPurchaseMapper;
import com.liule.ticket.utils.RedisIdWorker;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

/**
 * 订单落库事务的验证：正常落库、库存不足回滚、超限购回滚。
 * 用票档 3（看台 B，库存 3000，限购 4），测试用户固定 999002，
 * 结束后把测试用户的订单和购买记录删掉、库存加回去。
 */
@SpringBootTest
class OrderCreateTest {

    private static final Long TIER_ID = 3L;
    private static final Long SESSION_ID = 1L;
    private static final Long USER_ID = 999002L;

    @Autowired
    private IOrderService orderService;

    @Autowired
    private ITicketTierService ticketTierService;

    @Autowired
    private UserPurchaseMapper userPurchaseMapper;

    @Autowired
    private RedisIdWorker redisIdWorker;

    @AfterEach
    void cleanUp() {
        // 把测试用户买走的库存还回去，并清掉他的订单与购买记录
        LambdaQueryWrapper<TicketOrder> byUser = new LambdaQueryWrapper<TicketOrder>()
                .eq(TicketOrder::getUserId, USER_ID);
        int bought = Math.toIntExact(orderService.count(byUser));
        if (bought > 0) {
            int qty = orderService.list(byUser).stream()
                    .mapToInt(TicketOrder::getQuantity).sum();
            // lock_stock 必须跟着一起减。这些订单是 createOrder 建的，当时同步加过
            // lock_stock，且支付成功也不释放；只还 stock 的话，它每跑一次测试就往上垫一层 ——
            // total_stock = stock + lock_stock 会静默破掉，且没有任何断言会红。
            ticketTierService.update()
                    .setSql("stock = stock + " + qty
                            + ", lock_stock = lock_stock - " + qty)
                    .eq("id", TIER_ID)
                    .update();
        }
        orderService.remove(byUser);
        userPurchaseMapper.delete(new LambdaQueryWrapper<UserPurchase>()
                .eq(UserPurchase::getUserId, USER_ID));
    }

    private Integer stockOf(Long tierId) {
        TicketTier tier = ticketTierService.getById(tierId);
        return tier == null ? null : tier.getStock();
    }

    @Test
    void createsOrderAndDeductsDbStock() {
        int before = stockOf(TIER_ID);
        long orderId = redisIdWorker.create_ID("test");

        orderService.createOrder(orderId, USER_ID, TIER_ID, SESSION_ID, 2);

        TicketOrder saved = orderService.getById(orderId);
        assertThat(saved).isNotNull();
        assertThat(saved.getStatus()).isZero();
        assertThat(saved.getQuantity()).isEqualTo(2);
        assertThat(saved.getExpireTime()).isAfter(java.time.LocalDateTime.now().plusMinutes(14));
        // 金额 = 票档单价 × 数量
        assertThat(saved.getAmount()).isEqualByComparingTo(
                ticketTierService.getById(TIER_ID).getPrice().multiply(java.math.BigDecimal.valueOf(2)));
        assertThat(stockOf(TIER_ID)).isEqualTo(before - 2);
        assertThat(userPurchaseMapper.getQuantity(USER_ID, SESSION_ID)).isEqualTo(2);
    }

    @Test
    void rollsBackEverythingWhenOverPurchaseLimit() {
        int before = stockOf(TIER_ID);

        // 票档 3 的限购是 4：先正常买 4 张，再买 1 张
        orderService.createOrder(redisIdWorker.create_ID("test"), USER_ID, TIER_ID, SESSION_ID, 4);
        assertThat(stockOf(TIER_ID)).isEqualTo(before - 4);

        assertThatThrownBy(() -> orderService.createOrder(
                redisIdWorker.create_ID("test"), USER_ID, TIER_ID, SESSION_ID, 1))
                .isInstanceOf(BizException.class);

        // 关键：失败那次必须整体回滚 —— 库存、限购计数都不能留下痕迹
        assertThat(stockOf(TIER_ID)).isEqualTo(before - 4);
        assertThat(userPurchaseMapper.getQuantity(USER_ID, SESSION_ID)).isEqualTo(4);
        assertThat(orderService.count(new LambdaQueryWrapper<TicketOrder>()
                .eq(TicketOrder::getUserId, USER_ID))).isEqualTo(1);
    }

    @Test
    void rollsBackDbStockWhenTierHasNoStock() {
        // 把库存直接压成 0，模拟"Redis 说还有，DB 其实没了"
        ticketTierService.update().setSql("stock = 0").eq("id", TIER_ID).update();

        int before = stockOf(TIER_ID);
        assertThat(before).isZero();

        assertThatThrownBy(() -> orderService.createOrder(
                redisIdWorker.create_ID("test"), USER_ID, TIER_ID, SESSION_ID, 1))
                .isInstanceOf(BizException.class)
                .hasMessageContaining("库存不足");

        assertThat(stockOf(TIER_ID)).isZero();
        // 库存不足时不该动限购兜底表
        assertThat(userPurchaseMapper.getQuantity(USER_ID, SESSION_ID)).isNull();
        assertThat(orderService.count(new LambdaQueryWrapper<TicketOrder>()
                .eq(TicketOrder::getUserId, USER_ID))).isZero();

        // 把库存恢复，免得影响后续测试
        ticketTierService.update().setSql("stock = 3000").eq("id", TIER_ID).update();
    }

}
```

```java
        Long userId = UserHolder.getUser().getId();
        TicketOrder order = getById(orderId);
        if (order == null) {
            return Result.fail("订单不存在");

    @Override
    public Result listMyOrders(Integer status) {
        Long userId = UserHolder.getUser().getId();
        List<TicketOrder> orders = list(new LambdaQueryWrapper<TicketOrder>()
                .eq(TicketOrder::getUserId, userId)
                .eq(status != null, TicketOrder::getStatus, status)
                .orderByDesc(TicketOrder::getCreateTime));

        if (orders.isEmpty()) {
            return Result.ok(List.of());
        }

        // 一次把演出 / 场次 / 票档全查回来再按 id 装，不做 N+1。
        // 订单列表是"我的"页每次进来都要拉的，N+1 会随订单数线性变慢。
        Map<Long, Show> shows = showService.listByIds(
                        orders.stream().map(TicketOrder::getShowId).distinct().toList())
                .stream().collect(Collectors.toMap(Show::getId, s -> s));
        Map<Long, ShowSession> sessions = showSessionService.listByIds(
                        orders.stream().map(TicketOrder::getSessionId).distinct().toList())
                .stream().collect(Collectors.toMap(ShowSession::getId, s -> s));
        Map<Long, TicketTier> tiers = ticketTierService.listByIds(
                        orders.stream().map(TicketOrder::getTierId).distinct().toList())
                .stream().collect(Collectors.toMap(TicketTier::getId, t -> t));

        List<OrderVO> vos = orders.stream()
                .map(o -> toVO(o, shows.get(o.getShowId()), sessions.get(o.getSessionId()), tiers.get(o.getTierId())))
                .toList();
        return Result.ok(vos);
    }

    /** 单条订单装配，走一次库。列表走下面的重载，批量查。 */
    private OrderVO toVO(TicketOrder order) {
        Show show = showService.getById(order.getShowId());
        ShowSession session = showSessionService.getById(order.getSessionId());
        TicketTier tier = ticketTierService.getById(order.getTierId());
        return toVO(order, show, session, tier);
    }

    private OrderVO toVO(TicketOrder order, Show show, ShowSession session, TicketTier tier) {
        OrderVO vo = new OrderVO();
        vo.setOrder(order);
        if (show != null) {
            vo.setShowName(show.getName());
            vo.setPoster(show.getPoster());
        }
        if (session != null) {
            vo.setSessionName(session.getSessionName());
            vo.setSessionTime(session.getSessionTime());
        }
        if (tier != null) {
            vo.setTierName(tier.getName());
            vo.setSeatArea(tier.getSeatArea());
        }
        return vo;
    }
```

```java
    /**
     * 把订单占用的 quantity 张票还回库存。取消订单、支付超时失效都走这里。
     * <p>
     * 四个地方都要还原：Redis 库存、Redis 限购计数、DB 库存（stock 与 lock_stock 同一条
     * UPDATE 一起改）、DB 限购兜底表。
     * 少还任何一个，都会让用户"取消了却买不回来"或者库存凭空变多。
     */
    private void releaseStock(TicketOrder order) {
        int quantity = order.getQuantity();

        // 1) Redis 库存。
        //    必须先判断 key 是否存在 —— INCRBY 会把不存在的 key 当成 0 再加，
        //    直接补就是凭空造出 quantity 张票（DB 才是库存的权威值）。
        String stockKey = RedisConstants.SECKILL_STOCK_KEY + order.getTierId();
        if (Boolean.TRUE.equals(stringRedisTemplate.hasKey(stockKey))) {
            stringRedisTemplate.opsForValue().increment(stockKey, quantity);
        }

        // 2) Redis 限购计数退回。
        //    不退的话，用户取消后想重新抢会被自己上一次的计数挡住，看起来像"限购没释放"。
        String orderedKey = RedisConstants.SECKILL_ORDERED_KEY + order.getSessionId();
        if (Boolean.TRUE.equals(stringRedisTemplate.hasKey(orderedKey))) {
            Long left = stringRedisTemplate.opsForHash()
                    .increment(orderedKey, String.valueOf(order.getUserId()), -quantity);
            if (left != null && left <= 0) {
                // 退到 0 就把 field 删掉，别在 Hash 里留一堆 0
                stringRedisTemplate.opsForHash()
                        .delete(orderedKey, String.valueOf(order.getUserId()));
            }
        }

        // 3) DB 库存（权威值）。stock 与 lock_stock 一条 UPDATE 一起改，理由同 createOrder。
        //    ge("lock_stock", quantity) 是【重复归还】的守卫：lock_stock 是 INT UNSIGNED，
        //    重复归还减成负数会被 MySQL 拒绝（BIGINT UNSIGNED value is out of range）并炸掉事务。
        //    加守卫后重复归还表现为影响 0 行 —— 记日志即可，不要抛。
        boolean returned = ticketTierService.update()
                .setSql("stock = stock + " + quantity
                        + ", lock_stock = lock_stock - " + quantity)
                .eq("id", order.getTierId())
                .ge("lock_stock", quantity)
                .update();
        if (!returned) {
            log.warn("订单 {} 库存回补影响 0 行：lock_stock 不足，可能已归还过", order.getId());
        }

        // 4) DB 限购兜底表
        userPurchaseMapper.decrease(order.getUserId(), order.getSessionId(), quantity);
    }
```

```java
    public Result cancel(Long orderId) {
```

```java
    @Resource

    @Resource

    @Override
    @Transactional(rollbackFor = Exception.class)
    public void issueTickets(TicketOrder order) {
        TicketTier tier = ticketTierService.getById(order.getTierId());

        // 座位号占位序号：从"这个票档已经出了多少张"往后排。
        // 不做选座所以并发下可能重号，票号(主键)仍然是唯一的 —— 见「已知取舍」。
        int issued = Math.toIntExact(count(new LambdaQueryWrapper<Ticket>()
                .eq(Ticket::getTierId, order.getTierId())));

        List<Ticket> tickets = new ArrayList<>(order.getQuantity());
        for (int i = 0; i < order.getQuantity(); i++) {
            Ticket ticket = new Ticket()
                    // 订单号是票号的天然前缀，同一个订单出的票号连号，对账时一眼能看出对应关系
                    .setId(redisIdWorker.create_ID("ticket"))
                    .setOrderId(order.getId())
                    .setUserId(order.getUserId())
                    .setShowId(order.getShowId())
                    .setSessionId(order.getSessionId())
                    .setTierId(order.getTierId())
                    .setRealName(order.getRealName())
                    .setIdCard(order.getIdCard())
                    .setQrCode(UUID.randomUUID().toString(true))
                    .setStatus(0);

            // 站票/通票不生成座位号；对号入座填占位
            if (tier != null && Integer.valueOf(0).equals(tier.getSeatType())) {
                ticket.setSeatNo(tier.getSeatArea() + "-" + (issued + i + 1));
            }
            tickets.add(ticket);
        }
        saveBatch(tickets);
    }

    @Override
    public Result listMine() {
        Long userId = UserHolder.getUser().getId();
        List<Ticket> tickets = list(new LambdaQueryWrapper<Ticket>()
                .eq(Ticket::getUserId, userId)
                .orderByDesc(Ticket::getCreateTime));
        return Result.ok(tickets);
    }

    @Override
    public Result refreshQr(Long ticketId) {
        Long userId = UserHolder.getUser().getId();
        Ticket ticket = getById(ticketId);

        if (ticket == null) {
            return Result.fail("票不存在");
        }
        if (!ticket.getUserId().equals(userId)) {
            return Result.fail("无权查看他人的票");
        }

        ticket.setQrCode(UUID.randomUUID().toString(true));
        updateById(ticket);
        return Result.ok(ticket);
```

```java
    @Override
    @Transactional(rollbackFor = Exception.class)
    public Result pay(Long orderId) {
        Long userId = UserHolder.getUser().getId();
        TicketOrder order = getById(orderId);

        if (order == null) {
            return Result.fail("订单不存在");
        }
        if (!order.getUserId().equals(userId)) {
            return Result.fail("无权操作他人订单");
        }
        if (Integer.valueOf(1).equals(order.getStatus())) {
            return Result.fail("订单已支付");
        }
        if (!Integer.valueOf(0).equals(order.getStatus())) {
            return Result.fail("订单当前状态不可支付");
        }

        // 支付时限到了：在这里顺手把订单置为已失效并回补库存。
        // 严格来说这件事应该由延迟队列在到期那一刻主动做（Plan 3），
        // 现在这样"等用户来支付才发现"的懒处理会漏掉那些再也不回来的用户 ——
        // 他们的订单会一直挂在"待支付"，占着库存。
        if (order.getExpireTime().isBefore(LocalDateTime.now())) {
            order.setStatus(4).setCancelTime(LocalDateTime.now());
            updateById(order);
            releaseStock(order);
            return Result.fail("订单已超时失效，请重新抢票");
        }

        // 「不接真实支付」是设计文档附录 A 决策 7。这里模拟第三方支付回调成功。
        order.setStatus(1).setPayTime(LocalDateTime.now());
        updateById(order);

        // 这里【故意】不动 lock_stock，也不动 stock。
        // lock_stock 的语义是「被已下单、且未取消的订单占用」——支付成功只是把订单
        // 从待支付推进到已成交，占用关系并没有解除，所以两列都不动。这正是
        // total_stock = stock + lock_stock 在支付环节保持不变的原因。
        // ⚠ 别"顺手"在这里补一个 lock_stock - n：那会让已成交的票从 lock_stock 里消失，
        // 不变量当场破掉（tier 1 是 400 = 398 + 2，减完就成了 400 ≠ 398 + 0）。
        ticketService.issueTickets(order);
        return Result.ok(orderId);
    }
```

## Task 10: Redisson 重构缓存互斥锁

**Files:**

- Modify: `src/test/java/com/liule/ticket/utils/CacheClientTest.java`

**Interfaces:**
- Consumes: `RedissonClient`（Bean 已在 `RedissonConfig` 里，一直没人用）
- Produces: 对外行为不变——`CacheClient` 的四个 public 方法签名一个都不动

**背景**：`CacheClient` 现在用的是 `setIfAbsent` 手搓的锁，`rebuild` 的 `finally` 里无条件 `delete(lockKey)`。Plan 1 的「已知取舍」里就记着这个缺陷：**重建耗时超过锁的 10 秒 TTL 时，锁早已自动释放并被别人重新持有，此时删的是别人的锁**，于是两个线程同时重建。

换 Redisson 只是换了个 API，**缺陷不会自动消失**——如果还是「请求线程抢锁 + 线程池线程解锁」，就只能用 `forceUnlock()`，那等于换了个名字继续删别人的锁。真正要改的是**抢锁的位置**：把抢锁挪进重建任务内部，让加锁和解锁落在同一个线程上。Step 3(c) 的注释里写了完整推理。

> 这个 Task 不阻塞主线，可以放到最后做，也可以跳过。它对应设计文档技术点对照表的第 10 项「分布式锁 Redisson」，而 `RedissonConfig` 里的 `redissonClient` Bean 目前**全项目零引用** —— 面试官扫一眼会问"你配了 Redisson 但哪儿用了"。

**(c) `rebuild` 改成"先在同一线程里抢锁，抢到才重建"**：

```java
    /**
     * 异步重建。整个过程跑在线程池的线程里，不能抛异常出去，否则线程池会静默吞掉。
     * <p>
     * <b>为什么抢锁要放在这里，而不是在 queryWithLogicalExpire 里先抢锁再提交任务？</b>
     * <p>
     * 因为 Redisson 的 {@code unlock()} 会校验"当前线程 == 持锁线程"。如果抢锁发生在请求线程、
     * 重建跑在线程池线程，解锁就只能用 {@code forceUnlock()}（跳过持有者校验）——
     * 而那样一来，万一重建耗时超过了租期，锁早已自动过期并被别人重新持有，
     * 这个 forceUnlock 就又把别人的锁删了，跟原来手搓的那版缺陷一模一样，
     * 白换 Redisson。把抢锁挪进任务内部，加锁和解锁就都是同一个线程，
     * 可以用正规的 {@code unlock()}，持有者校验才真正起作用。
     * <p>
     * 代价是每个读到过期数据的请求都会提交一个任务，抢不到锁的任务立刻返回。
     * 这是几次内存操作的事，比"用错解锁 API 导致重复重建"划算得多。
     */
    private <R> void rebuild(String key, String lockKey, Class<R> type,
                             Supplier<R> dbFallback, Duration ttl) {
        RLock lock = redissonClient.getLock(lockKey);
        boolean locked = false;
        try {
            // tryLock(等待时间=0, 租期=10s)：
            //   等待时间给 0 —— 抢不到立刻放弃，不排队不阻塞（逻辑过期的全部意义就是不阻塞）
            //   显式给租期 —— 不给的话 Redisson 会启用"看门狗"，每 10 秒自动续期到 30 秒兜底，
            //   一次重建失败就会白占着锁半分钟
            locked = lock.tryLock(0, RedisConstants.LOCK_SHOW_TTL, TimeUnit.SECONDS);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return;
        }
        if (!locked) {
            // 别人正在重建，本次什么都不用做
            return;
        }

        try {
            // 双重检查：从"读到过期"到"抢到锁"之间，可能已经有别的线程重建完了
            String latest = stringRedisTemplate.opsForValue().get(key);
            if (StrUtil.isNotBlank(latest)) {
                RedisData latestData = JSONUtil.toBean(latest, RedisData.class);
                if (latestData.getExpireTime().isAfter(LocalDateTime.now())) {
                    return;
                }
            }

            R fresh = dbFallback.get();
            if (fresh == null) {
                // 数据被删了：清掉缓存，交给调用方的空值缓存策略接管
                stringRedisTemplate.delete(key);
                log.warn("缓存重建时数据已不存在，key={}", key);
                return;
            }
            setWithLogicalExpire(key, fresh, ttl);
        } catch (Exception e) {
            log.error("缓存重建失败，key={}", key, e);
        } finally {
            // 同线程解锁，Redisson 会校验持有者。
            // 万一重建真的慢过了 10 秒租期、锁已经易主，这里 unlock 会抛
            // IllegalMonitorStateException，而不会误删别人的锁 —— 这正是换 Redisson 要买的东西。
            // 抛出来的异常会回到线程池，所以自己接一下，只记日志。
            try {
                lock.unlock();
            } catch (Exception e) {
                log.warn("缓存重建释放锁失败（多半是重建耗时超过了租期），key={}", key, e);
            }
        }
    }
```

删掉原来的 `tryLock(String)` 私有方法，以及不再用到的 `BooleanUtil` import。

> `rebuild` 原来的调用点签名没变（多传的只是 lockKey，本来就传了），不用改。

## 已知取舍（面试会被问到，先记下来）

| 点 | Plan 2 的做法 | 更好的做法 / 什么时候改 |
|---|---|---|
| 超时订单不会自动失效 | 只有用户点支付时才发现超时 | Plan 3 的 ZSet 延迟队列，到期主动扫 |
| 回补的票直接放回公开池 | `INCRBY stock` | Plan 3 优先 ZPOPMIN 给候补队列 |
| 限购上限取**票档**的 `purchase_limit`，计数记在**场次**上 | 照设计文档 6.1 的 Lua 写法 | 语义上等价于"整场次限购 max(各票档限购)"。要严格按票档限购就把 key 换成 `seckill:ordered:{tierId}` |
| 消费者异常时也 ACK | 一条毒消息不会堵死队列 | 丢单靠日志人工兜底。Plan 3 可以加重试 N 次后转死信 stream |
| 缓存重建改成「先无条件提交任务，再在任务里抢锁」 | 抢不到锁的任务立刻返回，代价是几次多余的任务提交 | 换来的是加锁/解锁同线程，Redisson 的持有者校验真的生效。这是 Task 10 的核心设计，别改回去 |
| 座位号是占位序号 | `区域-已出票数+序号`，并发可能重号 | 票号(主键)唯一，不影响功能。要真座位得先做选座 |
| 静态 `SECKILL_SCRIPT` 每次执行都从 classpath 读脚本 | Lettuce 内部有脚本缓存（EVALSHA），首次 EVAL 之后走 SHA | 量级再大可以把脚本内容缓存成 String 直接传 |
| 抢票前每次查一次 DB 拿票档和场次 | 单行主键查询，微秒级 | 真要省可以把票档元信息也预热进 Redis |
| 支付是模拟的 | 直接改状态 | 设计文档附录 A 决策 7 已确认 |
